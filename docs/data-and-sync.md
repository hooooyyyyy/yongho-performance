# 기록 보존과 클라우드 연결 계획

## 이번 변경과 현재 사용법

이번 단계는 데이터 계층과 동기화 기반을 준비한다. 로그인 UI, 실제 클라우드 연결, 자동 동기화, 실제 AI 호출은 아직 활성화하지 않는다. 설정이 없어도 앱은 이전처럼 로컬에서 작동한다. 기준 루틴 파일·추천 중량·운동 구성은 변경하지 않는다.

앱은 `storage.js`의 기존 함수를 사용하고, 함수는 `localWorkoutRepository`에 위임한다. 클라우드는 별도 `supabaseWorkoutRepository`를 주입하는 `syncEngine`을 사용한다. 서버를 사용하지 않는 로컬 저장 경로에는 네트워크 요청이 없다.

## IndexedDB v3 → v4

DB 이름 `yongho-performance`, 기존 sessions/sets/meta와 인덱스, 기존 ID를 그대로 유지한다. v4는 outbox와 conflicts만 추가한다. upgrade 트랜잭션에서 모든 기존 행에 메타데이터를 덧붙인다. 트랜잭션이 실패하면 업그레이드 전체가 롤백된다. 기존 DB 삭제·초기화 코드가 없다.

| 항목 | 정책 |
| --- | --- |
| 세션 ID | 기존 `날짜:dayId` 유지. 같은 날 같은 루틴은 기존처럼 한 세션 |
| 세트 ID | 기존 ID 유지. ID 없는 입력은 `날짜:dayId:exerciseId:setIndex` |
| sessionId | 세트에 세션 연결 키 추가 |
| createdAt | 기존 createdAt/startedAt/updatedAt 순으로 사용. 모두 없으면 기록 날짜 00:00 UTC를 보조값으로 사용하며 실제 입력 시각이라는 뜻이 아님 |
| updatedAt | 기존 값을 유지. 이후 로컬 변경 시 갱신 |
| revision | 각 로컬 변경마다 UUID. 시간 비교 대신 동시 수정 탐지에 사용 |
| deletedAt | 삭제한 세트는 tombstone으로 보존. 조회·출석·분석에서 제외 |
| outbox | 기록 저장/삭제와 동일한 트랜잭션으로 생성. 행별 최신 revision을 보관 |
| conflicts | 충돌한 양쪽 내용을 별도 보존. 원본에 자동 승자 적용 안 함 |

세션 생성·수정·완료는 트랜잭션 안에서 읽고 쓰므로 동시 호출의 덮어쓰기를 줄인다. condition/restOverrides/exerciseNotes 패치는 해당 객체 키 단위로 병합한다. 명시적으로 같은 세트 ID를 저장하면 삭제 취소로 취급한다. 추가 버튼은 삭제 이력을 포함한 최대 setIndex 다음 번호를 사용한다. 삭제한 기본 세트는 세션을 다시 열어도 재생성되지 않는다.

v4를 적용한 뒤 v3 코드로 되돌리면 낮은 버전의 openDB가 열리지 않을 수 있다. 배포 롤백 시 DB 버전 4를 유지한 코드로 배포해야 하며 DB를 삭제해서 해결하면 안 된다. 업그레이드가 막히면 다른 탭/PWA를 닫고 다시 연다. Safari 저장 공간 삭제는 브라우저 자체 제약이므로 JSON 백업은 계속 제공한다.

## 백업 호환

기존 version 1 백업을 읽는다. 새 version 2 백업에는 삭제 표식과 충돌 사본도 포함한다. sessions/sets 배열은 유지한다. 가져오기는 전체 검증 후 단일 트랜잭션으로 병합한다. 같은 내용은 중복으로 처리하고, 같은 ID에 내용이 다르면 현재 기록을 유지하면서 백업 내용을 conflicts에 보관한다. 시각만으로 최신 기록을 선택하지 않는다. 안내에 새 기록·중복·충돌 개수를 표시한다. 백업에 계정 토큰·API 키·서버 접근 자격은 포함하지 않는다.

충돌 목록 UI와 항목별 해결 UI는 실제 계정 연결 단계에서 추가한다. 그 전에도 충돌한 내용은 백업 파일에서 확인할 수 있다. 공개 저장소에 백업을 올리지 않는다.

## 첫 로그인 시 병합

1. Supabase 인증 후 계정 ID를 확인한다.
2. `engine.preview()`는 서버의 해당 계정 기록을 읽고 업로드/다운로드/중복/충돌 개수와 상세 내용을 반환한다. 로컬/서버 기록에 쓰지 않는다.
3. UI에서 사용자에게 병합 내용을 보여준다. 세션·세트 단위로 분류되므로 숫자는 세션 수만 뜻하지 않는다.
4. 사용자가 업로드를 확인했을 때만 `engine.confirm(plan)`을 호출한다.
5. 확인 후 이 기기의 기록을 해당 계정에 연결한다. 미리보기 뒤 기록이나 계정이 바뀌면 다시 확인하도록 중단한다.
6. 기존 기록 ID가 다른데 같은 날짜·루틴·운동·setIndex인 경우 후속 UI에서 중복 후보로 추가 표시해야 한다. 현재 자동 중복 기준은 ID와 내용이다. 다른 ID는 임의 삭제하지 않는다.

현재는 하나의 로컬 저장 공간이다. 한번 연결한 계정과 다른 계정의 병합은 차단한다. 로그아웃은 로컬 기록을 삭제하지 않는다. 계정 전환 UI는 계정별 로컬 DB 격리를 구현한 후 제공해야 하며, 다른 사람의 계정으로 현재 기록을 자동 전송하면 안 된다.

## 동기화·충돌 정책

서버의 행 키는 `(user_id, kind, id)`. sessions/sets의 기존 필드를 payload JSONB에 그대로 보존해 루틴 스냅샷·긴 일지·향후 확장 필드를 손실 없이 전송한다. 서버는 단조 증가 version을 관리한다. 기기는 마지막으로 확인한 version을 meta에 기록한다.

- 로컬 저장은 항상 먼저 완료하고 outbox를 남긴다.
- 큐가 없으면 원격 변경을 내려받는다. 삭제 표식도 내려받으며 화면에서 제외한다.
- 큐가 있으면 마지막 확인한 서버 version과 같은 경우만 CAS RPC로 업로드한다.
- 양쪽 수정·수정 대 삭제 충돌은 현재 로컬 내용을 유지하고 양쪽 사본을 보존한다. 서버에도 기존 내용이 유지된다. 큐를 지우지 않는다.
- 첫 병합에서 같은 ID에 다른 내용은 충돌로 분류한다. 일지·세트를 추측해서 합치지 않는다.
- 네트워크 실패 시 큐가 유지된다. 업로드 직후 응답 손실 시 동일 payload 재전송은 서버에서 중복 처리한다.
- 전송 중 로컬 변경은 revision 확인으로 보호한다. 새 기록의 큐를 지우거나 다운로드로 덮어쓰지 않는다.
- 실제 연결 때 인증 완료/online/앱 복귀 및 로컬 저장 후 debounce로 sync를 실행한다. 첫 병합 승인을 저장한 계정에 한정하며 한 번에 하나의 sync만 실행한다. 실패 재시도는 지수 backoff, 로그아웃/계정 변경 시 작업 중단을 연결해야 한다.
- 충돌 해결 UI는 사용자가 선택한 내용을 새 revision으로 로컬에 저장하고, 검토한 remoteVersion을 기준 version으로 갱신한 뒤 CAS 재시도해야 한다. 충돌은 백업까지 보존하고 해결 이력을 남긴다.

지금은 개인용 전체 스냅샷을 페이지별로 가져온다. 서버에 없는 행을 삭제로 간주하지 않는다. 데이터가 늘면 서버 순번 기반 변경 피드를 추가한다. set/session 부모 연결은 payload.sessionId이며 세트만 있던 과거 기록도 허용하기 위해 SQL FK를 강제하지 않는다.

## Supabase 연결에 필요한 설정

사용자 프로젝트를 생성하거나 외부 연결을 실행하지 않았다. 연결 단계에서 필요한 것은 프로젝트 URL과 공개 publishable key(기존 anon key도 가능)이며, 비밀 service-role key를 요청하거나 브라우저에 넣지 않는다.

1. 사용자 소유 프로젝트에 `supabase/migrations/202610020001_workout_sync.sql` 적용.
2. `supabase/tests/workout_rls.sql` 실행 후 두 계정/익명 접근 검증.
3. Auth에서 사용할 이메일 로그인 등을 선택하고 리디렉션 URL을 `https://hooooyyyyy.github.io/yongho-performance/`로 등록. 로컬 개발 URL은 별도로 등록.
4. `.env.example`의 VITE_SUPABASE_URL/VITE_SUPABASE_PUBLISHABLE_KEY를 배포 환경변수로 설정. 이 값만 공개 번들에 포함 가능.
5. Supabase 클라이언트와 인증 UI를 연결하고 위 병합·충돌 흐름을 구현. 자동 동기화는 첫 승인 이후 활성화.

RLS는 소유자 읽기만 허용한다. 익명 접근과 직접 INSERT/UPDATE/DELETE는 거부한다. 쓰기는 UID 검사·계정 일치 검사·version 비교를 수행하는 RPC만 허용한다. 물리 삭제는 제공하지 않는다. 삭제 이력을 정리하는 작업은 모든 기기의 확인 정책이 생기기 전에는 실행하지 않는다.

## iPhone 배포 후 확인

배포 전 JSON 백업을 저장한다. 업데이트 후 기존 세션·17세트·일지가 그대로 보이는지, 빈 반복수가 0으로 바뀌지 않았는지, 새 세트 저장·삭제 후 재실행 결과, 백업 다운로드/재가져오기가 중복 처리되는지 확인한다. 실제 아이폰 IndexedDB는 개발 환경에서 직접 확인하지 못한다.
